# GH-99: parse_decompose_criteria reads stale field name after prompt-asset rename

## What shipped

Commit `27e1fa9` (PR #95) renamed the decompose stage's emitted JSON key from
`acceptance_criteria` to `proposed_criteria` in `commands/DECOMPOSE.md` and
`stage_specs/decompose_feat.md`, but `adw/orchestrator.py`'s
`parse_decompose_criteria` was never updated to match. It kept reading
`acceptance_criteria`, so it always returned `None` and `run_decompose`
blocked every ticket routed through decompose — even when the agent emitted
a well-formed, non-empty `proposed_criteria` array. This fix updates the
parser to read the new key.

## Behavior & breaking changes

`parse_decompose_criteria` (`adw/orchestrator.py:288-296`) now reads
`obj.get("proposed_criteria")` instead of `obj.get("acceptance_criteria")`.
Any caller still emitting the old `acceptance_criteria` key will no longer
be recognized — but that key was already stale as of PR #95, so this
restores the intended contract rather than breaking a working path.

## How it was verified

- `parse_decompose_criteria` reads `proposed_criteria` → `adw/orchestrator.py:292` (`ac = obj.get("proposed_criteria")`).
- A `success` outcome with a non-empty `proposed_criteria` array returns that list instead of blocking → `tests/test_decompose.py::test_run_decompose_success_returns_criteria`, asserts `criteria == ["a", "b"]` and `problem is None`.
- Regression test extracts criteria from a `proposed_criteria`-keyed payload → `tests/test_decompose.py::test_parse_extracts_criteria_from_status_block`, asserts `parse_decompose_criteria(...) == ["one", "two"]`.
- Full suite green → `uv run pytest -q`, 398 passed.
