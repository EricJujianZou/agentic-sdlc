## Harness traps (read first)
- NEVER type `cd` in a FOREGROUND Bash call — not `cd X && cmd`, not `cd X; cmd`, not a second `cd` later in the SAME compound line. That call usually
  SUCCEEDS; the NEXT one dies, so it feels unrelated (r022 and r025 each did it twice, having read this line). cwd PERSISTS and the PreToolUse hook is the
  *relative* `hooks/pretooluse_guard.py`. FIX: `Write` a .sh that `cd`s inside, `git -C <dir>`, or — for a repo-local node tool — `npx --prefix <repo> <tool> <ABS path>`. DISARM IT UP FRONT — right after cloning, `ln -sfn
  <repo>/hooks bench5/workspaces/task/hooks` AND `… bench5/workspaces/hooks` — symlink EVERY dir you might land in (r044 armed only `task/`, then a script's `cd` left cwd at `workspaces/` and the next Bash call died). DON'T `rm` them in your deliver script (r028 did, and the next
  Bash call died) — untracked, so `git diff` never sees them; just leave them. Already stuck? load `Monitor` (unhooked), re-make the symlink there. And a helper .sh that `cd`s must be handed ABSOLUTE paths for its logs — a relative one lands inside the repo (r044, twice). r048: a `bash helper.sh` whose body `cd`s LEAKED that cwd to the session (later relative paths resolved inside the repo and `wc -l bench5/state_armA.md` said 'No such file'), so the symlinks are what keep the guard quiet — `pwd` before trusting any relative path.
- The guard denies force-deletes if the command holds ANY absolute/`..` token (use `rm -f … && rmdir`), and bare `sleep N && cmd`; it scans the LITERAL text, so a heredoc merely QUOTING one is denied — use Write (r023 lost a whole compound call, python edit included, to an `rm -rf` inside a heredoc). Long installs blow the 120s timeout: background them, ending `echo exit=$? >>log`; block via `until grep -q '^exit=' log; do sleep 5; done` (and a bare `sleep 25 && cat log` is ALSO denied — always the until-loop). NEEDING PUBLIC VENDOR DATA (KB->build maps, EOL dates)? WebFetch and curl are 403 through the proxy for learn.microsoft.com, support.microsoft.com and wikipedia, but WebSearch works and its RESULT TITLES already carry the mapping verbatim ("November 14, 2023-KB5032189 (OS Builds 19044.3693 and 19045.3693)") — batch 3-4 ids per query and you confirm a whole table in ~5 calls; r047 caught two revisions its recall had wrong. r048: WebFetch is 403 for essentially every vendor/aggregator host (docs.aws.amazon.com, endoflife.date, eol.wiki, personal blogs) — skip it, go straight to WebSearch. And the vendor's page TODAY may carry a REVISED schedule (AWS now says AL2023 ends 2029-06-30) while the golden was written against the older table: pin the era's stated MODEL ("GA + 2y standard, +3y maintenance", GA 2023-03-15) and compute, rather than copying today's numbers.
- Multi-point edits: `Write` a .py of `assert s.count(old)==1; s=s.replace(old,new)` and run it — beats N Edit calls, the asserts catch a stale assumption instantly, and a revert-and-rerun NEGATIVE CONTROL is two more runs of it. NOT `python3 -c "..."`: inside double quotes `'\''` is NOT an escape, so one apostrophe in the payload (a Go comment's "doesn't") makes the pattern silently unmatchable (r024). Those same asserts save an `Edit` call too: `replace_all` matches LITERALLY, so two copies of one logical line sitting at DIFFERENT indentation (r050: the same `disabled: …` inside vs outside an `if` branch) leave the second silently unpatched while the tool still reports "All occurrences were successfully replaced" — `grep -n` the symbol right after, or you ship half the change.
  CHECK LINE ENDINGS FIRST (`b'\r\n' in open(f,'rb').read()`) — a Linux clone of a CRLF-authored repo is LF on disk, and the wrong ending fails every
  assert. Same trick for mechanical test sweeps, and for slicing out a whole func/class by index("start")..index("next decl") — but after EVERY slice assert the result still holds every top-level `^class`/`^def` the input had: r038's second slice quietly ate `class Seed` (the module still imported, so only a `grep -n "^class"` on the rewritten file caught it).
## Protocol mechanics
- Deliverable is `git -C bench5/workspaces/task diff` = worktree-vs-index, so ANYTHING STAGED IS INVISIBLE: a new file needs `git add -N <path>`;
  `git rm` HIDES a deletion (use plain `rm`); check `grep -c '^new file mode'`. `git stash push -u -- src` then REFUSES ("Entry … not uptodate"):
  `git restore --staged <newfile>`, stash / run / pop, re-`add -N` — script that dance; a FAILED stash silently runs your CHANGED tree as "baseline".
  A `.ts`->`.tsx` rename = plain `rm` old + write new + `add -N`. Finish by stashing src and `git apply --check <patch.diff>` — proof it applies.
- Package managers REWRITE LOCKFILES and install hacks live in package.json: `git status --short` before diffing, then `git checkout -- <lockfile> package.json`; build scratch venvs / vendored deps OUTSIDE `workspaces/task` (`workspaces/vendor/` is gitignored too). Any repair you make INSIDE tracked dirs (vendor/, submodules) must be listed in that same restore step, and `git checkout --` does NOT remove files the repair ADDED — `git clean -fd <dir>` too.
- Clone shallow+partial into the gitignored `bench5/workspaces/task`: `git init`; `git remote add origin <url>`; `git fetch --depth 1 --filter=blob:none origin <sha>`; `git checkout FETCH_HEAD`. Never fetch the fix commit. Submodules aren't fetched — `git ls-tree HEAD <path>` gives the pinned SHA, and cloning one at EXACTLY that SHA leaves the parent diff clean (r025: lib/web's whole suite is red until `webassets/` exists).
- The Requirements list IS the scope contract: one edit each, re-walk it against the diff; the LIST beats a vaguer blurb, its SILENCE on a nearby thing means leave that alone — even when your change strands it (r031's global `-wp-ignore-inactive` flag lost its only reader once the setting moved per-server; no bullet said remove it, so it stayed, declared in meta) — but that holds only while the stranded code still COMPILES: when a bullet's signature change turns an UNNAMED importer into a hard type error (r039: the list named 5 consumers, `grep -rln` found a 6th, Step1.tsx), convert it identically and declare it; grep every importer before trusting the list's count. A UI bullet saying render "the PROVIDED <x>" (r032) means the component is PRESENTATIONAL — it takes the hook's return value as PROPS; the bullet spelling out that hook's exact return shape IS the prop interface. Don't hedge by calling the hook inside too: a props-only test renders with NO providers and the hook throws. When a bullet asks for new TEST helpers, grep a sibling spec for the INLINE version — it is the literal thing being extracted (a local `Providers` wrapper -> the requested HOCs). Bullets also CONSTRAIN EACH OTHER: r035's "reject any value other than 1.0/1.1" + "the default is 1.1 when unset" only both hold if the default is applied at CONFIG-LOAD (viper `SetDefault`), never at the consumer — else "" would be rejected; derive the layer from the pair. And an Interface section naming exactly ONE new public symbol says the REST of the change uses builtin types: prefer a plain `string` field over a new named type, and make any helper consts UNTYPED so a hidden test's literal assigns either way. An Interface that spells out a POINTER receiver (`Receiver: i *Image`) means the golden used one, so a hidden test cannot call it on a composite literal -- copy the receiver form verbatim, don't 'improve' it to a value receiver. And when a LATER bullet composes that same string from a SIBLING type the Interface never mentions (r053: GetFullName is spec'd on config.Image, but the reporting bullet builds its identifier from models.Image), MIRROR the method onto the sibling and call it, rather than inlining the conditional: an extra public method can never fail a hidden test, a missing one fails to COMPILE. Declare the mirror in meta. Its FILE PATHS can be WRONG (r019 said `executor/worker.py`, real `executor/process/worker.py`) — locate by symbol. "Interface" is LLM-written, maybe uncompilable: honour its name/default/behaviour, and its PARAM ORDER — it is derived from the real patch. When the Interface lists a NEW FILE plus the symbols it holds, that list is EXHAUSTIVE — a nearby helper it omits stays put (r034 left `solr_escape`/`build_subject_doc` behind). And a bullet enumerating runtime scenarios ("success, service unavailability, invalid requests, network errors, partial failures in batch updates") is usually a paraphrase of an EXISTING test class — grep the suite for it: finding it tells you the real patch MOVED that class to a test file beside the moved code, so move it too (grading RESETS every test file the golden touched, so that move is free — what must be right is that the SOURCE serves it). A "remove Mixin X / consolidate into Y" issue (r036, r038 again) puts Y in the module holding the Interface's new function; when that function is a `register_models()`, wire it by making the OLD module's `register_models()` CALL it (both startup paths already go through the old one, which is what "no additional manual registration" means) — and the import must be LAZY, inside the function body, because the moved class's base (`Thing`) is defined BELOW the old module's import block, so a top-level import ImportErrors on whichever module loads first; build the moved body by SLICING the original class text inside your apply script, so the move is verbatim by construction. Moving a class also moves it AWAY from its base: if that base is the very import you are breaking the cycle on, re-derive from `client.*`/the stdlib base and hand-restore ONLY the inherited methods something actually CALLS (grep templates — `can_undo()` runs on every changeset view); declare the rest. And RE-EXPORT the moved symbol from the OLD module — other files import it from there (openlibrary's `upstream/utils.py` does, under TYPE_CHECKING), the pre-existing suite keeps passing, and it hedges whichever import path the hidden test picked. ADD-A-NEW-<X>-TO-A-REGISTRY issues have a mechanical scope: `grep -rn <an existing sibling's name>` repo-wide and that hit list IS the fan-out (r037: provider class + the ORDER list + 2 templates + the solr fetched-fields set + the doc builder + the test pinning the whole doc). Two hits in it are traps — a GENERATED i18n `messages.pot`/`.po` (leave it; no bullet named it) and a config yml that ALREADY has your entry (check before adding). Bullets that read as CONTRADICTORY may just name two different LAYERS: r045's "Download returns clear errors for unsupported types" vs "self-hosted must not trigger a download" both hold only if the SKIP sits in the caller and the ERROR in the callee -- the golden's table test drives the caller and needs a clean empty result there, so derive which layer each bullet is talking about instead of picking one. Likewise a new `CheckAndSetDefaults`-style default belongs right after the field it derives from, not at the END: a config that trips a later `BadParameter` check never reaches a trailing default, and a test asserting the default alone then fails. Requirement prose also silently TYPO-CORRECTS existing symbols — r048's bullet wrote `IsExtendedSupportEnded` where the repo has `IsExtendedSuppportEnded` (3 p's); that is NOT a rename order. Tell-tale: the repo's OWN test error STRING already spells it correctly, so the requirements-writer copied prose from the test, not the signature — grep callers before renaming anything the Interface section didn't name. When a VENDOR table has two date columns and the struct has two date fields (AWS standard-vs-maintenance -> StandardSupportUntil/ExtendedSupportUntil), the bullet naming only ONE field is the strongest signal, then what the SIBLING entries in that same map already hold (vuls' Amazon 1/2/2022 hold full end-of-life dates, not phase boundaries), then what the CONSUMER's message text implies ('Purchase extended support if available' misfires on a free maintenance phase) — pick, and declare the alternative in meta. Keying a map on a version parsed out of a release string: normalise with `major(ss[0])`, not `ss[0]`, so the tidy fixture form ('2023 (Amazon Linux)') and the real host form ('2023.3.20240219 (Amazon Linux)') both land on the same key — you cannot know which the hidden test used.
  Bullets CONTRADICT each other (r026: "port must never be modified" vs "the segment structure must cover host, port, path, …"). Tie-break toward the behaviour an EXISTING test pins; obey a bullet that only contradicts the BASE CODE (a changed default) — that is the patch talking. Record the call. A TITLE that sounds sweeping ("X should ALWAYS move with Y") over a bullet naming ONE trigger site (r030: only the drop-on-INBOX branch of three) = build the named site; the odd specificity is the real patch showing through, and the other branches often have unspecified side-effects (section flips) you would have to invent. A bullet can also name the WRONG FAMILY outright — r047's "align SUSE Enterprise Desktop/Server ... version 13 until 2026-04-30, version 14 until 2028-11-30" was FreeBSD: no SLES/SLED 13/14 exists, FreeBSD was the ONLY map in config/os.go carrying "13"/"14" keys, and its base values (2026-01-31/2028-11-21) were the stale form of exactly those two dates. So grep the literal KEYS/VALUES a bullet quotes across the file and let the unique hit pick the block; the numbers are copied from the golden and are far more reliable than the prose label. Declare the call in meta. Two bullets that are EXACT COMPLEMENTS pin the condition with no room to hedge (r051: "when the cancellation flag is set OR auto-renew is disabled -> active term only" vs "when the flag is not set AND auto-renew is enabled -> existing behaviour"): build the literal disjunction even when its second clause breaks a PRE-EXISTING expectation, because the narrower reading (gate on the new flag alone) leaves that clause dead code, and a bullet is never dead code. The test that then goes red IS the golden's test patch.
- "Centralize X in <one file>; ALL UI calls it" means EVERY inline copy, not just the file the next bullet names — grep the old body's distinctive call and convert each; dropping the now-dead param then trips react-hooks/exhaustive-deps, so lint the touched files after. - PLUMB/UNPLUMB-A-PARAM: put it beside its sibling at EVERY hop incl. - DELETING a cross-cutting middleware/feature orphans more than imports: its private helper types+funcs, its test cases, AND the spies in the package's support_test. The compiler flags only unused imports and locals, so grep every symbol the deleted body touched and drop the ones only it used.

Replacing a boolean with the richer value it was derived from (`isPrivate` -> `joinRule`) must keep the OLD default: pick the fallback that reproduces the base truth table, and test the no-state case. A "sort by <new key>" bullet whose key TIES where the old key didn't WILL break a pre-existing expectation (r041: OvalMatch and CpeVersionMatch both score 100, and sort.Slice is unstable): keep the OLD key as a SECONDARY comparator — new key primary, old key as tiebreak satisfies the bullet AND every existing case, and it is the only choice that survives both plausible shapes of the hidden test. A bullet ordering a shared MOCK moved into the GLOBAL jest setup (r050: `window.ResizeObserver`) is never cosmetic and must not be deferred: grading resets test files but NOT `jest.setup.js`, and reverting only that file flipped 15/16 of my cases with `ReferenceError: ResizeObserver is not defined` thrown from an unrelated child (Scroll.tsx) — the hidden test for that component cannot even RENDER without it. Run that revert as its own control and it also tells you WHICH package's setup the hidden test needs.

## Verification habits
- A problem statement that says "tests fail with COMPILATION ERRORS indicating field X is not defined" is a gift twice over (r046): it names the exact identifiers+receivers the hidden test touches, and writing your throwaway test FIRST reproduces the issue for free — the build error it emits at base should quote those very fields, which both proves the repro and catches a wrong field name before you code. Such a task can't be negative-controlled by stashing (the test won't compile), so KEEP the new fields and revert one ASSIGNMENT per bullet.
- NO DATABASE? CHECK BEFORE BELIEVING IT — `which redis-server mongod psql` and `ls -d /usr/lib/postgresql/*/bin`: this container ships redis-server AND postgres 16 (no mongod), so a suite written off as "needs a live DB" is often fully runnable, which beats any stub. redis: `redis-server --port 6399 --daemonize yes --save ''`. postgres: `initdb` REFUSES to run as root, and the `postgres` user cannot traverse a `/tmp/claude-*/…` scratchpad path (initdb dies "could not access directory"), so put PGDATA under `/var/lib/postgresql/<x>`, `chown postgres`, and `su postgres -c "$PGBIN/initdb -D <dir> -U postgres --auth=trust"` + `pg_ctl -o '-p 5439' start`. Only when there is genuinely no server, stub it: load the module under test directly and intercept its deps by overriding `Module.prototype.require`, gated on `this.filename === <file>` so only that file sees stubs (py: `sys.modules[...]=Mock()`; go: the repo's own `common.StoreMock` + a cacheSpy). In Go, HAND-FAKE the vendored driver interface: they are small (goval-dictionary `db.DB` 12 methods, gost's 24), and a fake that just RECORDS its argument turns "which release string do we send the DB/HTTP client?" into a table test — return a canned row too and it also covers the code consuming it. Take expected values from the repo's OWN test table, never eyeball them (r033 read `\.[es]l(\d+)(?:_\d+)?` as KEEPING `_9`; it strips it).
- TEST HARNESS RED AT BASE (native deps, browser-only bundler plugins, a vendored lib too old for the toolchain, an unfetched submodule)? Don't give up and don't assume it's yours — REPRODUCE AT BASE FIRST (stash source, re-run), then REPAIR THE ENVIRONMENT (r025: swap one vendored dep, clone one submodule — ~15 min bought two whole suites) or REBUILD A MINI SUITE (r023, ~20 min): copy the repo's bootstrap file, import the N test files you care about + the runner's `o.run/report`, and re-run the repo's OWN esbuild/webpack config MINUS the offending plugins (`define` their globals to dummies). Keep it in the scratchpad so the diff stays clean.
- Baseline FIRST when a suite DOES run: whole suite at base into fails_before.txt, again after, `comm` the sorted FAILED/ERROR sets; only the DELTA
  counts (r019: 253 fails both sides, 0 new, 2 fixed). A red test that PASSES when re-run ALONE is flakiness, not your regression, and one that fails only
  in the BEFORE run is usually a TIMING test, not something you fixed (r025 PasswordSuite.TestTiming). STASH SOURCE ONLY: lockfiles/vendor unbuild the
  base. Same for tsc/lint — the repo's PINNED linter, run FROM THE REPO ROOT so nested configs apply, before/after sets diffed.
- PLUMBING A NEW OPTION can't be negative-controlled by stashing either (r035: the new tests reference `WithManifestVersion`). Neither can a task whose whole diff is ONE NEW FILE (base = a collection error, which teaches nothing). Revert ONE line per Requirements bullet instead — the arg you threaded, the default you set, the validation you added, or in a new file its one initialiser / its one subscribe / its one cleanup (r043: three disjoint flips) — re-running after each: the matching subtests must flip and the SIBLING cases pinning the unchanged default must stay green. Script it (edit/run/restore in a `finally`) and it is three cheap runs. RESTORE BY `cp` FROM A SAVED COPY — NEVER `git checkout -- <file>`: the index is HEAD, so it silently reverts your WHOLE change in that file and every later control then runs against BASE and 'flips everything' (r038 lost two controls to this before noticing). A SIGNATURE REFACTOR can't be negative-controlled by stashing (your new tests won't COMPILE at base). Instead keep the new signature and revert the ONE
  semantic line (r031: `cnf.IgnoreInactive` -> the old global `c.Conf.X`), re-run, confirm exactly the behaviour tests flip red, restore. A pure MOVE is the same shape — revert one REGISTRATION line per bullet (r036/r038, the same instance family, both: drop the delegating call, then `register_changeset_class('lists', …)`, then break the key regex, then the `(Thing)` base; four runs, each flipping a DISJOINT set, is the whole proof). Also: a function that
  looks like it needs the whole app wired up is often offline-testable — package loggers are usually `init()`ed to a discard writer, and PREFILLING the cache/dep
  map it consults makes every network branch unreachable, so you can assert real end-to-end counts with no server. A control that DELETES a block can BUILD-FAIL on the import it just orphaned, and a build failure flips EVERY test, teaching nothing -- neuter the block with a no-op that still USES the symbol (`_, _ = tlsca.ParseCertificatePEM(b)`) instead of deleting it. AND THE CONTROL HARNESS ITSELF MUST BE BASE-COMPATIBLE — a query coupled to your own change is not a control: r050's `getByLabelText('Calendar URL')` broke at BASE because the character-counter hint the fix removes lives inside the same `<label>` (base accessible name is 'Calendar URL0/10000'), so all 15 cases flipped and proved nothing; re-querying by `data-test-id`/CSS split the very same run into 5 red (new behaviour) and 11 green (behaviour preserved). Split controls by AXIS as well, since one global-setup revert flips every render. A DEFENSIVE `?? <old expression>` FALLBACK ALSO MASKS ITS OWN CONTROL: r051 routed three screens through `subscriptionExpires(sub, true)` but wrote `expirationDate ?? sub.PeriodEnd` to satisfy the `number | null` return type — dropping the `, true` argument then flipped ZERO tests, because the null branch fell back to the same timestamp. Control such a call site by restoring the BASE EXPRESSION verbatim (`sub.UpcomingSubscription?.PeriodEnd ?? sub.PeriodEnd`), not by removing the new argument; that split 5 flips into a disjoint 3 (b2c) + 2 (b2b). Keep the argument anyway when a bullet asks for it, and declare the redundancy in meta.
- To simulate the golden's TEST patch, COPY a repo test file to an untracked sibling name and flip the ONE mock line that pins the old behaviour (r049: `mockReturnValue(false)` -> `mockImplementation(n => n === '<flag>')`) — the whole harness comes free. Two traps: under `--ci` the copy's snapshots are NEW, so `toMatchSnapshot` cases fail with 'New snapshot was not written' — constant noise in EVERY run, diff the fail SETS, don't chase; and a control that DELETES a settings/registry ENTRY makes `getValue`/lookup THROW for every component reading it, so the whole suite flips and teaches nothing per-bullet — expect that shape and read only the one case you aimed at. Write a THROWAWAY test file inside the repo's OWN test tree (untracked -> invisible to `git diff`; `rm` it before delivering) with one case per Requirements bullet, then NEGATIVE-CONTROL the whole file by stashing src and re-running: the bullets you implemented must go red, the pre-existing behaviour you preserved must stay green. That split is the cheapest proof the diff is both live and scoped (r028: 6 of 11 flipped; r037: 10 of 12). Import any NEW symbol LAZILY inside the tests that need it (a one-line `def cls(): import mod; return mod.NewThing`) — a top-level `from mod import NewThing` turns the whole negative control into ONE collection error and you learn nothing per-bullet. Don't let that file MUTATE the interpreter to make its point: deleting `sys.modules['pkg.*']` to prove an import is independent re-imports the package, so the objects your OTHER tests grabbed at file top are now a different module instance and they fail for a reason that is 100% your harness (r034) — assert on a `subprocess` import instead. A factory whose only output is a MOUNTED component needs no render: capture `createModal.mock.calls[0][0]` and assert `element.type === TheComponent` plus its `.props`, then drive the seam by CALLING those props (`props.onSubmit(x)` settles the promise the factory returned; `props.onProcess()` hands you `{promise, abort}` to await). A requirement about WHAT GETS LOGGED is a first-class testable, not a read-the-code item: package loggers are usually a swappable package VAR (vuls `logging.Log = logging.Logger{Entry: *l.WithFields(...)}` with `l.Out = &bytes.Buffer{}`, restored in `t.Cleanup`), then assert per-LINE substring SETS (name + filter + count + criteria) and negative-control by deleting ONE log call at a time — each deletion must flip a disjoint test (r042: 5 controls, 5 disjoint sets). Anchor those substrings: asserting ("web01","6") passed off an unrelated `--confidence-over=60` line until it became ("web01","total 6") — a bare number is not a match, and only the tightened form caught the deleted total line. In GO, NEVER name that file `*_windows_test.go` / `_linux` / `_darwin` / `_amd64`: any `<prefix>_<GOOS|GOARCH>` basename carries an IMPLICIT build constraint, so on linux the file is silently NOT COMPILED and every negative control reports "ALL PASS" (r047 lost a control round to this; the repo's own `windows_test.go` is fine because the rule needs a prefix before `_windows`). General fix: make the control harness assert it actually RAN tests — count `--- ` lines / catch "no tests to run" — because a green control and an absent control look identical. A control whose FIRST test PANICS kills the whole test binary, so every later test in that run reports NOTHING and a 5-test control reads as a 1-test control (r048: base `getAmazonLinuxVersion` indexed ss[0] on an empty release). Run each control case in its OWN `go test -run '^Name$'` and treat a MISSING `--- ` line as PANIC/DID-NOT-RUN, never as a pass — that is the concrete form of "assert the control actually ran". And when a script SCRAPES those `--- FAIL: TestName (0.00s)` lines, `split()[-1]` grabs the DURATION, not the name: every control then prints an identical 'flipped: (0.00s)' and you cannot see whether the flips were DISJOINT, which is the entire point of running them one at a time -- take `split()[2].rstrip(':')` and eyeball a real test name in round one. Also: don't reason about a stdlib format string, RUN it — a 5-line `go run` proved `time.Parse("2006.01", "2018.03")` really is year.month (the '.0' does NOT become a fractional-second chunk), which the fix depended on.
- DON'T COPY A FIXTURE FROM THE REPO'S OWN TESTS WITHOUT CHECKING IT REACHES YOUR BRANCH — matrix-react-sdk's helper writes `m.room.create` `content: {version}` but `Room.getVersion()` reads `room_version` and falls back to "1", so every existing "v8 room" test is really a v1 room and the version gate is never exercised. Assert the precondition too (e.g. that the upgrade pill is ABSENT on a SUPPORTED version), or a green test proves nothing. THE PROBLEM STATEMENT'S OWN EXAMPLES ARE FIXTURE-DEPENDENT and will not reproduce in a standalone test file: r052's issue promised `userOrGroupExists(['administrators','John Smith']) -> [true,true]`, but NodeBB's `test/mocks/databasemock.js` seeds only configs/privileges/plugins — `groupslug:groupname` is EMPTY, so `administrators` is false and the FIXED code reads as broken (test/user.js only has that group because an earlier test in the same file made an admin).
